# PDF design and implementation specification

Use [DATA_AND_COPY.md](DATA_AND_COPY.md) for every value, date, source, and status. Use [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md) for the brand. The twelve revised images are printable page references, not PDFs generated by the current app. Their revision adds the exact official logo, larger text, clearer graphs and explicit arithmetic comparisons. Several templates require proposed export features. A separate vector PDF sample demonstrates the print implementation without changing the application.

## Export families and scope

The current app generates one doctor-report PDF containing confirmed laboratory history and recorded medication name, strength, and instructions. It also exports confirmed laboratory rows as CSV. It currently has no date filter, section picker, template library, or built-in PDF preview.

| Export family | Proposed behavior | Existing data available |
|---|---|---|
| Health summary | One-page visit overview of latest confirmed values and recorded medications | Yes; new layout and latest-result selection |
| Lab history | Complete confirmed history, or selected markers and date range | Current complete-history export exists; filters are new |
| Medication record | Recorded medication details, with optional schedules and dose history | Yes; schedules/events are new PDF sections |
| Device measurements | Date-bounded steps, daily average heart rate, and weight | Yes; entire PDF export is new |
| Source appendix | Included source reports, original-file availability, optional correction history | Yes; entire PDF section is new |

The export hub should offer the first four families. The source appendix is an optional section, not a fifth competing main action. Marker detail may offer “Export this marker.” CSV remains a secondary format choice. A backup is a separate encrypted file format and never appears as a PDF template.

The default report uses one profile. Include confirmed observations only. An export options page shows the active profile, period, included sections, language, and A4/Letter size. These controls are proposed. The implementation agent must not pretend existing exporter parameters already support them.

## Shared print system

### Page geometry

| Property | A4 | US Letter |
|---|---:|---:|
| Trim size | 210 × 297 mm | 215.9 × 279.4 mm |
| PDF points | 595.28 × 841.89 pt | 612 × 792 pt |
| Left/right margins | 17 mm | 17 mm |
| Top/bottom safe margins | 16 mm | 16 mm |
| Usable width | 176 mm | 181.9 mm |
| First-page identity/header allowance | Up to 43 mm | Up to 43 mm |
| Continuation header allowance | 11 mm | 11 mm |
| Footer band | 9 mm, within safe area | 9 mm, within safe area |

Use a real white page and the final Vezuna Living Color identity. Every page uses the exact `assets/brand/logos/lockup-ink.svg`: two curved V/person strokes and one dot, with the supplied outlined Noto Sans wordmark. Place it about 42 mm wide at upper left, preserve its aspect ratio, and leave at least 4 mm clear space. Never substitute a leaf, sprout, generic V, newly typeset wordmark, or decorative symbol. The real PDF embeds the SVG paths directly. A bold pine `#123B46` document heading establishes the brand. Use restrained category bands in records mint `#71E2CC`, care coral `#FF8A65`, trends lavender `#B8ABFF`, and activity citron `#DDF27C`, always with dark pine text. The bands can be 6–9 mm tall; keep their combined coverage modest. Body text uses `#152E35`, secondary text `#526C74`. White space remains the majority of every page. Do not print a solid app background, a dark cover, large mobile cards, or shadows across the paper.

Charts can use vivid category-colored dots and bars, with pine outlines or labels where the hue alone lacks contrast against white. A pine trend line with colored observation dots remains clear on an office printer. Color identifies the content family, not medical severity. Clinical status always has its full text and may use a compact semantic symbol. The result should be lively and recognizable without spending ink on decorative full-page fills.

The A4 page is the default image format. Letter reflows rather than scales down. Do not clip, squeeze type, or reduce margins to force equal page counts. Page count may differ between formats.

### Typography and spacing

Use embedded bundled Noto Sans regular and bold. Main document title is 24–26 pt, profile name 13 pt bold, section title 15–16 pt bold, body/table text 11.5–12 pt, row/header labels 11 pt bold, explanatory notes 11 pt, footer 9 pt. Essential values, units, instructions, warnings and graph labels stay at least 11 pt. Latest-result callouts can be 22–24 pt. Body leading is 1.35–1.4; notes use at least 1.3. Text is selectable in the actual PDF. If content does not fit, add a page instead of shrinking type.

Use 2/3/4/6/8 mm space steps. Table cells have 3 mm vertical and 2 mm horizontal padding. Rules are 0.25 mm. Table rows have a minimum height of 10 mm, growing with content. Reference text wraps naturally and never becomes ellipsized. Align numeric columns on the decimal separator when possible; attach the unit to its value rather than leaving it on another page. Prefer two-line result rows and labelled blocks to six or seven narrow columns.

Header order is exact Vezuna lockup, document title, Ana Silva and optional birth date, included collection period. Put the generation timestamp in the footer or a separate metadata area labelled “Generated”; never let it appear to be a collection date. “Synthetic example · Not a clinical document” appears as a small but readable sample marker in every design image. This marker belongs to fixtures, not real user exports.

Every continuation page repeats the profile name and document title. Every page footer has “Vezuna · Private health record,” generation date, and “Page X of Y.” Produce total page count only after pagination. The footer never overlaps content.

### Tables and charts

The main results table uses plain headings: Test, Latest result, Recorded reference, and Comparison with reference. Put the collection date below the result; place a long comparison on its own secondary line when needed. On a 176 mm content width use approximately 37/39/43/57 mm. The word “Test” is easier to read than “Marker.” A row's textual status is authoritative; color alone never carries meaning. Sparse results can use full-width labelled blocks instead of a table.

History tables use Date, Result, Recorded reference, and Source. They run vertically, rather than placing an unbounded number of dates in tiny horizontal columns. Use approximately 25/34/49/68 mm on A4. Grouping may omit repeated source labels if the relationship remains explicit. Repeated rows are real readings, not copied summaries.

History charts use the full 176 mm content width and a plot height of 48–60 mm; a dedicated single-test page allows 75–90 mm. Summary charts can sit side by side at about 84 mm wide and 45–55 mm high. Labels remain at least 11 pt. Show a visible y-axis unit, readable ticks, each measured dot, its actual value, and collection dates placed at their real relative intervals. Do not spread dates evenly unless the intervals are equal. The canonical hemoglobin series is 13.0, 12.8, 13.2 g/dL on 12 April, 15 July, and 28 October. Its example axis is 12–16 g/dL. The canonical LDL series is 146, 140, 132 mg/dL on 12 April, 15 July, and 14 October. Its example axis is 120–160 mg/dL with the recorded 130 reference shown as a labelled dashed line. These are example scales, not universal clinical thresholds.

Place two plain summaries next to each numerical history: “Change since first result” and “Change since previous result,” each with its baseline collection date and signed absolute difference. HGB uses +0.2 and +0.4 g/dL; LDL uses −14 and −8 mg/dL. Calculate from the selected compatible-unit series, not hidden results outside the export period. A missing comparison is “Not available,” never zero. Avoid diagnostic words, a score, or semantic red/green coloring of arithmetic changes.

Give the reader a short graph key: “Dots are recorded results. The reference comes from the source report. Changes are arithmetic differences, not a clinical assessment.” Connecting segments are visual guides between actual observations, not interpolated measurements. The canonical available history spans April–October 2026. Do not invent earlier years to suggest a longer history. Long real histories keep a readable full-period overview, an exact data table, and extra pages when required; never replace the whole history with only the latest three points.

Reference bands are permissible only when every included reading shares compatible reference bounds. If ranges differ, draw per-reading reference indicators or show the ranges only in the accompanying table. Missing ranges remain missing. Incompatible units use separate series. Text-only results have no numeric chart. A single numeric reading has a value/date and “One recorded result; comparison not available,” never a trend line. An optional single-point reference plot can locate that recorded number within its source range, but must not imply change over time. All charts have exact labelled values and an accessible text/table equivalent; add a data page if it cannot fit at the minimum type size.

The device template uses three stacked panels, each with a readable summary and a wide graph: daily step bars, daily average heart-rate points/line, and sparse weight points. Print its available history explicitly as seven days. Do not label the heart-rate graph “Resting heart rate.” Do not draw a weight reading on a day with no reading. Exact first/previous changes and baseline dates are in DATA_AND_COPY. For dose history use a labelled categorical day timeline; do not draw a numeric trend or adherence percentage. Source lists and empty selections need no graph.

## Pagination and accessibility

Keep a section title with its first two table rows or first complete result block. Repeat table headers on every continuation page. Never split a row unless one row exceeds the entire usable page height; then split it with an explicit continued label and repeat its identifying marker/date. Keep the latest value, unit, reference, and status together.

A marker's chart should follow its history on the same page when space permits. If it must move, repeat the marker name and unit above the chart. Do not leave a section heading at the foot of a page. Medication names and their instructions stay in one row. Long multilingual strings increase row height. Avoid inserting blank pages when a section is taller than a fresh page.

The one-page summary is one page only when the selected information fits legibly. With a larger real dataset, paginate into “Health summary, continued.” Do not silently omit selected results or shrink text below the specified minimum. A selectable “latest four markers” overview would be a separate, explicitly scoped option, not a default truncation rule.

The implementation target is a tagged PDF with document language, title metadata, logical heading structure, table headers, meaningful reading order, and descriptions for charts. Do not claim the current native PDF engines already produce these. If the rendering stack cannot provide tags, record the gap and provide a text/table alternative; do not rasterize text to match the mockups. Set PDF metadata only from safe filenames and selected profile content; exclude local vault keys and internal paths.

Check grayscale and ordinary office printing. Use labeled status words and, where useful, distinct symbols such as up/down arrows plus text. Do not use color or a red/green distinction alone. Respect the original unit and every sign, decimal separator, and source phrase. Verify accessibility and rendering with the actual output, not only the sample images.

## Expected export interaction

1. Choose an export family from More or Records. A marker detail can preselect its marker.
2. Review profile, period, sections, language, and paper size. Show included confirmed count and excluded unreviewed count. Keep original source files as a separate explicit future option, not a silent attachment.
3. Preview the actual generated document. The preview's page count and contents must match the saved bytes.
4. Save or share through the platform's native interface. Show a recoverable error if file creation fails. Canceling save is not data loss and should not look like an app failure.

The native share sheet is owned by the OS. Do not implement custom mail recipients, automatic sending, or a clinician address book as part of this redesign. No network is needed to generate the document. Export availability must remain independent of local-model installation and optional feature licensing.

Suggested filenames are `vezuna-ana-silva-health-summary-2026-11-01.pdf`, `vezuna-ana-silva-lab-history-2026-11-01.pdf`, and corresponding family names. Sanitize filenames and preserve the active profile scope. These meaningful filenames are proposed; the current exporter uses `vezuna-doctor-export.pdf`.

## Medical and privacy constraints

PDFs describe the record. They do not diagnose, prescribe, claim treatment efficacy, infer urgency, or calculate a wellness score. “Above report range” is the recorded reference comparison, not a disease label. Do not include unconfirmed OCR, hidden profile data, assistant-generated medical conclusions, or invented missing values.

Original and normalized numbers remain distinguishable. Qualitative text remains text. Source precision is preserved where the model stores it. The current formatter rounds to three decimals; the redesign should correct that implementation limitation instead of reproducing it. An absent reference is not “within range.” Ranges can differ by source and date.

PDF and CSV files are ordinary shareable documents, not encrypted backups. Their content leaves the vault boundary when the user exports them. `.vhbak` backups are passphrase encrypted and include structured records, but not original report file bytes. A source appendix must describe missing originals honestly after restore. It must not imply the original report is embedded in the exported PDF.

| Check | Expected result |

| Numeric fidelity | Original precision, signs, dates, and units survive PDF text extraction. |
| Pagination | Long names, long medication instructions, long reference text, 100+ rows, and section overflow do not clip or create blank pages. |
| Format and language | A4 and Letter reflow; EN/PT/ES text renders with accents; print grayscale remains understandable. |
| Accessibility | Text remains selectable; logical reading order and tags are checked where supported; every chart has exact textual values. |
| Delivery | Native save/share receives the previewed bytes; cancellation and failure preserve all health data. |
| Sparse data | Zero results, one numeric result, all-qualitative, missing references, absent medications, and missing originals display honestly. |

## Included vector print samples

`pdf-samples/vezuna-laboratory-history-a4.pdf` and `pdf-samples/vezuna-laboratory-history-letter-grayscale.pdf` are real two-page synthetic design samples. They contain the exact SVG logo paths, embedded Noto Sans, selectable 11–12 pt body/data text, actual-date graph geometry, first/previous comparisons, a plain graph key and a six-row exact history table. The continuation page contains TSH, the qualitative result, medication details and export scope. Generation and collection dates are separate. These samples demonstrate the print rules; they are not output from the current app or pixel copies of the raster mockups.

The reproducible source is `generation/build_pdf_samples.py`, using ReportLab and FontTools to render the existing SVG paths. A plain-text alternative and usage notes accompany the PDFs. Both sample documents were rendered with Poppler and visually inspected. Text, paper size, embedded fonts, absence of raster images and grayscale color operands were checked. The samples are not tagged PDF/UA; the implementation still needs the tagged structure and reading-order checks described above. Do not call them fully accessible solely because the text is selectable.

## Current implementation sources

Paths are relative to the repository root. `shared/src/commonMain/kotlin/app/vezuna/export/DoctorExport.kt` defines the current export model and confirmed-only filtering. `DoctorExamSections.kt` groups markers by canonical code and compatible unit. `DoctorChartGeometry.kt` handles actual dates and per-reading reference bounds. `DoctorReportFormat.kt` handles numbers and export dates. `ExportText.kt` supplies EN/PT/ES labels.

Native rendering lives in `shared/src/androidMain/kotlin/app/vezuna/export/AndroidPdfExporter.kt`, `shared/src/iosMain/kotlin/app/vezuna/export/IosPdfExporter.kt`, and `shared/src/jvmMain/kotlin/app/vezuna/export/JvmPdfExporter.kt`. Current Android output is A4; iOS output is Letter. Settings/export preparation lives in `shared/src/commonMain/kotlin/app/vezuna/ui/CareScreens.kt` and `AppController.kt`. Native delivery lives in `composeApp/src/main/java/app/vezuna/export/AndroidExportCoordinator.kt` and `iosApp/Vezuna/NativeExportView.swift`.
